# Ведение учебного курса

## 1. Изменение материалов курса

- Преподаватель изменяет задания, инструкции и учебные материалы в `master`.
- Изменения в `master` вносятся через отдельную ветку и Pull Request в соответствии с действующим ruleset.
- Pull Request должен содержать понятное описание изменения.
- Перед объединением необходимо проверить содержание файлов, ссылки и результаты автоматических проверок, если они настроены.
- Не следует объединять несвязанные изменения в одном Pull Request.
- Изменения `master`, сделанные после создания ветки задания, не переносятся автоматически в уже начатые студенческие работы. Если такое обновление необходимо, преподаватель отдельно сообщает студентам безопасный порядок действий.
- Нельзя изменять опубликованные задания задним числом без уведомления студентов.
- Изменения, влияющие на выполнение работы или начисление баллов, сопровождаются явным пояснением.

## 2. Подготовка веток задания

- Для каждого задания преподаватель создаёт от последнего актуального commit ветки `master` независимую ветку по шаблону `submissions/<задание>`, например `submissions/lab-01`.
- Ветки `submissions/*` не создаются друг от друга, не объединяются между собой и не объединяются обратно в `master`.
- Сразу после создания ветки преподаватель сохраняет полный идентификатор её первоначального commit — состояния `master`, от которого преподаватель создал ветку задания, — и сообщает его студентам вместе с названием задания. Он нужен студентам, которые начнут работу после принятия первых Pull Request.
- До объявления начала сдачи преподаватель получает подтверждение администратора, что действуют rulesets для `submissions/*` и `student/**/*`: аккаунт рабочей станции с ролью `Write` может создавать и обновлять студенческие ветки, но не может напрямую изменять, создавать или удалять ветки задания.
- Студент, начинающий работу после появления принятых Pull Request, самостоятельно переключается на сохранённый первоначальный commit задания и создаёт от него рабочую ветку. Создавать позднюю ветку от текущего состояния `submissions/<задание>` нельзя.
- Преподаватель сообщает студентам имя ветки задания, исходный commit, срок сдачи и директорию задания, которую будет проверять.

## 3. Работа со студенческими ветками и приём задания

- Для каждого задания используется отдельная рабочая ветка по шаблону `student/<группа>/student-<номер-студента-в-группе>/<задание>`.
- Компоненты имени ветки и личной директории берутся из обезличенного идентификатора таблицы успеваемости: идентификатору `b24-601_student_07` соответствуют ветка `student/b24-601/student-07/<задание>` и директория `b24-601/student-07/`.
- Студент выполняет и исправляет работу в этой ветке, после чего открывает Pull Request в соответствующую ветку `submissions/<задание>`.
- Преподаватель проверяет правильность base- и compare-веток, отсутствие унаследованных работ других студентов и нахождение изменений только в личной директории студента.
- Если студент создал ветку от более позднего commit и унаследовал принятую работу другого студента, преподаватель самостоятельно определяет дальнейшие действия. В зависимости от обстоятельств это может рассматриваться как нарушение правил самостоятельного выполнения задания.
- Проверка работы, вопросы и замечания оформляются непосредственно в Pull Request.
- Студент устраняет замечания в той же рабочей ветке и отправляет новые коммиты; они автоматически добавляются в открытый Pull Request.
- После принятия работы преподаватель выполняет squash merge. Студент не выполняет merge самостоятельно и не отправляет изменения непосредственно в ветку задания.
- Ветка `submissions/<задание>` используется как общая точка просмотра принятых работ всех студентов. Студенческий код из неё не переносится в `master`.
- Рабочая ветка после принятия не удаляется преподавателем или студентом и больше не используется. Объединённый Pull Request является окончательной сдачей задания; исправления и замечания должны быть обработаны до merge. Очистку ошибочных веток при необходимости выполняет только администратор организации.
- Преподаватель не изменяет студенческую ветку без необходимости. Если вмешательство требуется для устранения технической проблемы, он сообщает студенту, что и почему было изменено, и предварительно сохраняет исходное состояние ветки.
- Опубликованная история студенческой ветки не переписывается без обоснованной необходимости.
- Если студент случайно изменил локальную `master`, преподаватель помогает сначала сохранить работу в рабочей или резервной ветке и только затем восстановить локальную `master`.

## 4. Аудиторные компьютеры

- На аудиторном компьютере используется заранее подготовленный локальный клон репозитория.
- Для каждого клона задаются только локальные параметры `user.name` и `user.email`; параметр `--global` не используется.
- Преподаватель проверяет название текущего репозитория, адрес `origin`, техническую идентификацию компьютера, логин закреплённого аккаунта и доступ к GitHub.
- Студенты работают в отдельных рабочих ветках заданий, используя аккаунт текущего компьютера. При переходе на другое место они продолжают ту же ветку через аккаунт нового компьютера.
- Преподаватель и студенты не изменяют пароль, почту, второй фактор, способы восстановления и параметры доступа аккаунта рабочего места; о проблемах сообщается администратору.
- Личные аккаунты преподавателей и студентов не сохраняются в браузере или Git credential manager общего компьютера и не подменяют аккаунт рабочего места.
- Действие в GitHub, commit author и Pull Request определяют рабочее место, но не доказывают личность студента. Для идентификации используются ветка, директория, расписание и данные преподавателя.

## 5. Публикация списков и результатов

- Ведение таблиц успеваемости в GitHub является предлагаемой возможностью, а не обязанностью преподавателя.
- Если преподаватель решает вести таблицы в GitHub, до первой публикации он уведомляет студентов об использовании этого способа, расположении файлов и применяемых обезличенных идентификаторах.
- Если преподаватель решает не вести таблицы в GitHub, он удаляет из репозитория шаблонную директорию `study-groups/`, чтобы её наличие не вводило преподавателей и студентов в заблуждение.
- В `master` репозитория своего предмета преподаватель может вести таблицы успеваемости студентов, используя вместо ФИО идентификатор по шаблону `<номер-группы>_student_<номер-студента-в-группе>`, например `b24-601_student_07`.
- Для каждой учебной группы создаётся отдельная таблица в отдельном Markdown-файле. Рекомендуемая структура — директория `study-groups/` с файлами по шаблону `study-groups/<группа>.md`, например `study-groups/b24-601.md`.
- Не объединяйте несколько учебных групп в одной таблице без отдельной организационной необходимости: раздельные файлы упрощают сопровождение, проверку изменений и параллельную работу преподавателей.
- Номер студента берётся из используемой университетом системы, сопоставление в которой недоступно сторонним пользователям. Связь идентификатора с ФИО, личным аккаунтом GitHub или другими персональными данными не публикуется в учебном репозитории.
- В таблицах допускается указывать баллы за семестр, контрольные мероприятия и отдельные этапы курса только в объёме, необходимом для организации учебного процесса.
- В таблицах не размещаются ФИО, личные адреса, номера телефонов, данные документов, пароли, токены и другая информация, не требуемая для ведения курса.
- Преподаватель отвечает за актуальность опубликованных результатов и исправляет обнаруженные ошибки.

## 6. Безопасность

В репозитории нельзя размещать:
- пароли, токены и приватные ключи;
- закрытые решения и служебные материалы, не предназначенные для студентов;
- внутренние документы университета, не предназначенные для публикации;
- сведения, не относящиеся к учебному процессу.

Если секрет попал в GitHub, недостаточно удалить его следующим коммитом. Преподаватель прекращает дальнейшее распространение секрета и немедленно сообщает администратору, чтобы отозвать или заменить секрет и при необходимости очистить историю.

## 7. Разбор нарушений и ошибок

- GitHub сохраняет логи действий аккаунтов, которые могут быть разобраны при необходимости. Поскольку аккаунт рабочего места является общим, одного логина недостаточно для вывода о личности студента. Если для расследования требуется журнал аудита организации, преподаватель обращается к администратору.
- Перед исправлением нарушения следует сохранить сведения о ветке, коммитах, времени и затронутых файлах.
- Не следует сразу удалять ветку или переписывать историю, если это уничтожит сведения о произошедшем.
- О нарушении студентом правил сообщается ответственному преподавателю и администратору.
- Учебные и дисциплинарные санкции применяются в соответствии с правилами курса и университета.
