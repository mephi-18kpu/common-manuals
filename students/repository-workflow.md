# Работа с учебным репозиторием

В примерах используются следующие значения:

```text
Репозиторий:      2026-autumn-python-course
Группа:           b24-601
Студент:          student-07
Задание:          lab-01
Ветка задания:    submissions/lab-01
Исходный commit:  SUBMISSION_BASE_COMMIT
Рабочая ветка:    student/b24-601/student-07/lab-01
Рабочая директория: D:/Study
Личная директория:  b24-601/student-07/
```

Замените их значениями, которые сообщил преподаватель. Не копируйте имена веток из примера без изменений.

## 1. Первоначальное клонирование

Перейдите в директорию, предназначенную для учебных репозиториев, и выполните:

```bash
cd "D:/Study"
git clone https://github.com/mephi-18kpu/2026-autumn-python-course.git
cd 2026-autumn-python-course
```

Если преподаватель выдал другую ссылку для клонирования, используйте её. На аудиторном компьютере доступ выполняется через закреплённый за ним аккаунт GitHub; не заменяйте его личным аккаунтом и не переносите сохранённые данные для входа между компьютерами.

Проверьте адрес удалённого репозитория и состояние рабочей копии:

```bash
git remote -v
git status
```

Адрес должен указывать на репозиторий курса в организации `mephi-18kpu`.

## 2. Проверка идентификации компьютера

В каждом клоне администратор настраивает технического автора коммитов. Проверьте настройку:

```bash
git config --local --get user.name
git config --local --get user.email
```

Не изменяйте эти значения самостоятельно. Если они отсутствуют или не соответствуют компьютеру и курсу, обратитесь к преподавателю.

## 3. Создание рабочей ветки задания

Преподаватель создаёт для задания общую ветку `submissions/<задание>` и сообщает её первоначальный commit — состояние `master`, от которого была создана эта ветка. Пока в ветку задания не принят ни один Pull Request, рабочую ветку студента можно создать непосредственно от неё:

```bash
git fetch origin
git switch --no-track -c student/b24-601/student-07/lab-01 origin/submissions/lab-01
git push -u origin HEAD
```

Параметр `--no-track` не позволяет ошибочно связать рабочую ветку с общей веткой задания. Команда `git push -u origin HEAD` создаёт одноимённую удалённую студенческую ветку и настраивает дальнейшие короткие команды `git pull` и `git push`.

Если в `submissions/<задание>` уже приняты работы других студентов, не создавайте ветку от её текущего состояния. Используйте исходный commit, выданный преподавателем:

```bash
git fetch origin
git switch --no-track -c student/b24-601/student-07/lab-01 SUBMISSION_BASE_COMMIT
git push -u origin HEAD
```

Если исходный commit неизвестен, не угадывайте его и обратитесь к преподавателю. Если ветка по ошибке создана от более позднего commit, содержащего чужую принятую работу, прекратите работу и сообщите преподавателю. Не пытайтесь самостоятельно переписывать историю: преподаватель определит дальнейшие действия, а использование чужого решения может быть расценено как нарушение правил самостоятельного выполнения задания.

Перед первым push обязательно проверьте:

```bash
git branch --show-current
git status
```

Если рабочая ветка уже существует на GitHub, создавать её повторно не нужно:

```bash
git fetch origin
git switch --track origin/student/b24-601/student-07/lab-01
```

Если ветка уже существует и в локальном клоне:

```bash
git switch student/b24-601/student-07/lab-01
git pull --ff-only origin student/b24-601/student-07/lab-01
```

## 4. Начало каждого занятия

Откройте локальный репозиторий и проверьте его состояние:

```bash
cd 2026-autumn-python-course
git status
git branch --show-current
```

Текущей должна быть рабочая ветка выполняемого задания. При необходимости переключитесь на неё и получите собственные изменения с GitHub:

```bash
git switch student/b24-601/student-07/lab-01
git pull --ff-only
```

Если на другом компьютере ветка отсутствует локально, подключите её по инструкции из предыдущего раздела.

Не объединяйте в рабочую ветку обновившуюся `submissions/lab-01`: после начала приёма там могут находиться работы других студентов. Не объединяйте `master` без прямого указания преподавателя. Если преподаватель изменил материалы после начала задания, следуйте его отдельной инструкции.

## 5. Работа с файлами

Изменяйте файлы только внутри своей директории:

```text
b24-601/student-07/
```

Перед коммитом проверьте изменения:

```bash
git status
git diff
```

Добавляйте только нужные файлы, указывая их явно:

```bash
git add b24-601/student-07/path/to/file.py
git diff --cached
git commit -m "Краткое описание изменения"
```

Не используйте `git add .`, пока не проверили все отображаемые `git status` файлы.

## 6. Отправка изменений

После каждого завершённого этапа отправляйте коммиты в свою рабочую ветку:

```bash
git branch --show-current
git push
```

Если связь с удалённой веткой ещё не настроена, выполните:

```bash
git push -u origin HEAD
```

Обычный push разрешён, но удаление ветки и force-push запрещены ruleset. При отклонении non-fast-forward сначала получите собственные удалённые изменения; не пытайтесь обходить запрет.

## 7. Сдача задания через Pull Request

Перед созданием Pull Request убедитесь, что все изменения задания сохранены в коммитах и отправлены на GitHub:

```bash
git status
git branch --show-current
git push
```

На GitHub откройте раздел **Pull requests**, нажмите **New pull request** и выберите:

- в поле **base** — ветку задания, например `submissions/lab-01`;
- в поле **compare** — свою рабочую ветку, например `student/b24-601/student-07/lab-01`.

Перед созданием Pull Request проверьте вкладку **Files changed**. Изменения должны относиться только к текущему заданию и находиться в вашей личной директории. В названии укажите задание и обезличенный идентификатор, например `lab-01: b24-601_student_07`.

Преподаватель проверяет работу и оставляет комментарии в Pull Request. Для исправления замечаний измените файлы в той же рабочей ветке, создайте новые коммиты и выполните `git push`. Изменения автоматически появятся в открытом Pull Request.

Не объединяйте Pull Request самостоятельно и не отправляйте изменения непосредственно в `submissions/<задание>`. После принятия работы преподаватель выполняет squash merge, и принятая версия появляется в общей ветке задания.

## 8. После принятия работы

Ветка `submissions/<задание>` содержит принятые версии работ и не объединяется с `master` или ветками других заданий. Рабочая ветка `student/<группа>/student-<номер-студента-в-группе>/<задание>` после принятия не удаляется и больше не используется: объединённый Pull Request считается окончательной сдачей задания.

Для следующего задания преподаватель создаёт новую независимую ветку от актуальной `master`. Студент создаёт новую рабочую ветку от исходного состояния новой ветки задания, например:

```text
student/b24-601/student-07/lab-02
```

Не создавайте ветку следующего задания от предыдущей студенческой ветки или от `submissions` другого задания.

## 9. Просмотр веток и истории

Полезные команды, не изменяющие репозиторий:

```bash
git status
git branch --show-current
git branch --all
git log --oneline --decorate --graph -20
git diff
git diff --cached
```

Не переключайтесь на чужую студенческую ветку для внесения изменений.
